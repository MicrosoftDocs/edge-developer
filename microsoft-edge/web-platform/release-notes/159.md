## CSS features

The following new Cascading Style Sheets (CSS) features are included in Microsoft Edge.


<!-- ------------------------------ -->
#### `AccentColor` and `AccentColorText` follow `accent-color`

The `AccentColor` and `AccentColorText` system colors now reflect the element's effective `accent-color` value, instead of only the accent colors that are provided by the platform.

Use the `AccentColor` and `AccentColorText` system colors to reuse, in your own styles, the same colors that `accent-color` applies to form controls and other accented UI.

For example, the following CSS gives a custom element the same accent color as the checkbox that's next to it:

```css
.option {
  accent-color: rebeccapurple;
}

.option .custom-marker {
  background: AccentColor;
  color: AccentColorText;
}
```

See also:
* [`accent-color` CSS property](https://developer.mozilla.org/docs/Web/CSS/Reference/Properties/accent-color) at MDN.
* [System Colors](https://www.w3.org/TR/css-color-4/#css-system-colors) in _CSS Color Module Level 4_.
* [AccentColor / AccentColorText Demo](https://kyerebo.github.io/demos/system-accent-color/index.html)


<!-- ------------------------------ -->
#### Computed `background` values keep their layer count

The computed values of the `background-*` longhand properties, such as `background-repeat` and `background-size`, now keep the number of comma-separated values that you specified.  Previously, these computed values were repeated or truncated to match the number of layers in `background-image`.

Repeating and truncating still happen when the browser renders the layers, because they're part of the used value, not the computed value.  As a result, this change only affects what you read back, such as by using `getComputedStyle()`.

For example, in the following CSS, `background-repeat` has two values, while `background-image` has three layers.  The computed value of `background-repeat` still has the two values that you specified.

```css
.hero {
  background-image: url(a.png), url(b.png), url(c.png);
  background-repeat: no-repeat, repeat;
}
```

See also:
* [`background-image` CSS property](https://developer.mozilla.org/docs/Web/CSS/Reference/Properties/background-image) at MDN.
* [Appendix A: Coordinating List-Valued Properties](https://drafts.csswg.org/css-values-4/#linked-properties) in _CSS Values and Units Module Level 4_.


<!-- ------------------------------ -->
#### Scroll snap in single-axis scroll containers

Scroll snap now works separately for each axis in single-axis scroll containers, such as an element that has `overflow: auto clip`.

Previously, a single-axis scroll container captured snap areas on both axes, even on the axis that it can't scroll.  A snap area then couldn't align on that axis.

Now, when a snap area sets alignment on both axes, a single-axis scroll container only handles the axis that it scrolls.  The other axis goes up to the nearest ancestor scroll container that scrolls in that direction.

See also:
* [CSS scroll snap](https://developer.mozilla.org/docs/Web/CSS/Guides/Scroll_snap) at MDN.
* [`scroll-snap-type` CSS property](https://developer.mozilla.org/docs/Web/CSS/Reference/Properties/scroll-snap-type) at MDN.
* [CSS Scroll Snap Module Level 1](https://drafts.csswg.org/css-scroll-snap-1) - W3C Editor's Draft.
* [Single-axis scroll containers](./156.md#single-axis-scroll-containers) in _Microsoft Edge 156 web platform release notes (Oct. 22, 2026)_.


<!-- ------------------------------ -->
#### `CSSImportRule.styleSheet` can be `null`

The `styleSheet` property of the `CSSImportRule` interface now returns `null` when an `@import` rule has no associated stylesheet, such as when the `supports()` condition of the rule is `false`.

Use the `CSSImportRule.styleSheet` property to check whether a stylesheet is associated with an `@import` rule, before you access its properties:

```javascript
const importRule = document.styleSheets[0].cssRules[0];
if (importRule.styleSheet) {
  console.log(importRule.styleSheet.cssRules.length);
}
```

See also:
* [CSSImportRule: styleSheet property](https://developer.mozilla.org/docs/Web/API/CSSImportRule/styleSheet) at MDN.
* [The `CSSImportRule` interface](https://drafts.csswg.org/cssom/#the-cssimportrule-interface) in _CSS Object Model (CSSOM) Module Level 1_.

## Web APIs

The following new Web API features are included in Microsoft Edge.


<!-- ------------------------------ -->
#### Sanitizer API: `javascriptURLs` option

The Sanitizer API now provides the `javascriptURLs` configuration option and the `setJavascriptURLs()` method.  The `javascriptURLs` configuration option and the `setJavascriptURLs()` method control whether `javascript:` URLs that are used for navigation (such as in the `href` attribute of an `<a>` element) are removed when sanitizing HTML.

Previously, whether `javascript:` URLs were removed depended on the method that you used:
* The safe methods, such as `setHTML()`, always removed `javascript:` URLs.
* The unsafe methods, such as `setHTMLUnsafe()`, never removed `javascript:` URLs.

Now, removing `javascript:` URLs is an explicit part of the sanitizer configuration, which you can use with any method.

If you don't use the new option, the behavior is unchanged.

See also:
* [HTML Sanitizer API](https://developer.mozilla.org/docs/Web/API/HTML_Sanitizer_API) at MDN.
* [Sanitizer](https://developer.mozilla.org/docs/Web/API/Sanitizer) at MDN.
* [setJavascriptURLs()](https://html.spec.whatwg.org/#dom-sanitizer-setjavascripturls) in _HTML Standard_.


<!-- ------------------------------ -->
#### Prerendering cross-origin iframes

On a top-level page, to prerender all of the page's cross-origin iframes along with the page, use the following HTTP response header:

```http
Supports-Loading-Mode: prerender-cross-origin-frames
```

By default (that is, without using that response header), when a page is prerendered, the browser delays loading its cross-origin iframes until the prerendered page is activated.  When cross-origin iframes are critical to your application, this delay can negate many of the benefits of prerendering.

See also:
* [Speculation Rules API](https://developer.mozilla.org/docs/Web/API/Speculation_Rules_API) at MDN.
* [Prerendering cross-origin iframes](https://github.com/WICG/nav-speculation/blob/main/prerendering-cross-origin-iframes.md) - Explainer.
* [Prerendering Revamped](https://wicg.github.io/nav-speculation/prerendering.html).


<!-- ------------------------------ -->
#### Media Session API: `setMicrophoneActive()` and `setCameraActive()` return promises

The `navigator.mediaSession.setMicrophoneActive()` and `navigator.mediaSession.setCameraActive()` methods now return a `Promise` that resolves with `undefined`, instead of directly returning `undefined`.

If the associated document isn't fully active, the promise is rejected with an `InvalidStateError` exception.

See also:
* [MediaSession: setMicrophoneActive() method](https://developer.mozilla.org/docs/Web/API/MediaSession/setMicrophoneActive) at MDN.
* [MediaSession: setCameraActive() method](https://developer.mozilla.org/docs/Web/API/MediaSession/setCameraActive) at MDN.
* [setMicrophoneActive()](https://w3c.github.io/mediasession/#dom-mediasession-setmicrophoneactive) in _Media Session_.


<!-- ------------------------------ -->
#### Service worker static routing: Distinct error for cancelled raced requests

When a service worker uses a static routing rule with the `race-network-and-fetch-handler` source, and its `fetch` event handler calls `fetch(event.request)`, the browser reuses the raced network request instead of sending a second network request.

If the raced network request is cancelled before the response headers arrive, the promise that's returned by `fetch(event.request)` is now rejected with a `TypeError` that has a specific message: `The service worker race-network-and-fetch-handler request was cancelled before 'fetch()' settled.`  Previously, the message was the generic `Failed to fetch` message.

For example, a raced network request gets cancelled in the following situations:
* When your offline fallback timer resolves `event.respondWith()` first.
* When the navigation is aborted.

Use the new message to distinguish between these expected cancellations versus network errors.

See also:
* ["race-network-and-fetch-handler"](https://developer.mozilla.org/docs/Web/API/InstallEvent/addRoutes#race-network-and-fetch-handler) in _InstallEvent: addRoutes() method_, at MDN.
* [InstallEvent](https://w3c.github.io/ServiceWorker/#installevent-interface) in _Service Workers Nightly_.


<!-- ------------------------------ -->
#### Web Speech API: Timestamps for `SpeechRecognitionResult`

The `SpeechRecognitionResult` interface now has the `speechStartTime` and `speechEndTime` properties.  The `speechStartTime` and `speechEndTime` properties give the start and end times of the speech segment that was recognized, in seconds, relative to the start of the audio stream.

Previously, the Web Speech API didn't expose when a segment of speech occurred.  Use the `speechStartTime` and `speechEndTime` properties to associate transcribed text with a media timeline, such as to generate synchronized subtitle cues.

See also:
* [SpeechRecognitionResult](https://developer.mozilla.org/docs/Web/API/SpeechRecognitionResult) at MDN.
* [Web Speech API](https://developer.mozilla.org/docs/Web/API/Web_Speech_API) at MDN.
* [Update SpeechRecognitionResult with speech timing attributes](https://github.com/WebAudio/web-speech-api/pull/192) - pull request in the **WebAudio / web-speech-api** repo.


<!-- ------------------------------ -->
#### WebTransport: Datagram readable stream type

The `WebTransport()` constructor now accepts the `datagramsReadableType` option.

By default, incoming datagrams are exposed through a default `ReadableStream`.  If your application needs to read datagrams into buffers that you provide, by using a BYOB (bring your own buffer) reader, set `datagramsReadableType` to `"bytes"` to get a readable byte stream instead:

```javascript
const transport = new WebTransport(url, { datagramsReadableType: "bytes" });
```

See also:
* [WebTransport: WebTransport() constructor](https://developer.mozilla.org/docs/Web/API/WebTransport/WebTransport) at MDN.
* [`datagramsReadableType`, of type `ReadableStreamType`](https://www.w3.org/TR/webtransport/#dom-webtransportoptions-datagramsreadabletype) in _WebTransport_ at W3C.


<!-- ------------------------------ -->
#### WebTransport: Datagram writable streams and prioritization

The `createWritable()` method of `WebTransportDatagramDuplexStream` now creates independent `WebTransportDatagramsWritable` streams, which you can use to send datagrams.

Each writable stream has mutable `sendGroup` and `sendOrder` properties, which express the relative priority of the queued data in the same send group.  Microsoft Edge applies this ordering among datagram writable streams.

Microsoft Edge also reports the negotiated maximum size of outgoing datagrams, and discards writes that are larger than this size, as required by the WebTransport specification.

See also:
* [WebTransportDatagramDuplexStream: createWritable() method](https://developer.mozilla.org/docs/Web/API/WebTransportDatagramDuplexStream/createWritable) at MDN.
* [WebTransportDatagramsWritable](https://developer.mozilla.org/docs/Web/API/WebTransportDatagramsWritable) at MDN.
* [WebTransportDatagramsWritable Interface](https://www.w3.org/TR/webtransport/#datagram-writable) in _WebTransport_ at W3C, about datagram writable streams.


<!-- ------------------------------ -->
#### WebTransport: Send groups and send-stream prioritization

You can now assign outgoing `WebTransport` streams to send groups, and use the `sendOrder` property to prioritize streams within each group.  Previously, you could send data by using `WritableStream` objects, but you couldn't control how the browser prioritized the streams.

Statistics about sending are also available for streams and for send groups.  Transferring a `WebTransportSendStream` still works the same way as transferring a `WritableStream`.

See also:
* [WebTransportSendStream](https://developer.mozilla.org/docs/Web/API/WebTransportSendStream) at MDN.
* [WebTransportSendGroup](https://developer.mozilla.org/docs/Web/API/WebTransportSendGroup) at MDN.
* [Interface `WebTransportSendStream`](https://www.w3.org/TR/webtransport/#webtransportsendstream) in _WebTransport_ at W3C.


<!-- ------------------------------ -->
#### WebTransport: `WebTransportReceiveStream`

The new `WebTransportReceiveStream` interface is a subclass of `ReadableStream` that `WebTransport` uses for incoming unidirectional streams, and for the readable side of bidirectional streams.

The `getStats()` method of the `WebTransportReceiveStream` interface returns the following byte counters for the stream:
* `bytesReceived` - The number of bytes received from the network.
* `bytesRead` - The number of bytes delivered to your application.

See also:
* [WebTransportReceiveStream](https://developer.mozilla.org/docs/Web/API/WebTransportReceiveStream) at MDN.
* [Interface `WebTransportReceiveStream`](https://w3c.github.io/webtransport/#webtransportreceivestream) in _WebTransport_ at W3C.


<!-- ------------------------------ -->
#### WebTransport: Congestion control

The `WebTransport()` constructor now accepts the `congestionControl` option, and `WebTransport` instances now have a read-only `congestionControl` property.

Set the `congestionControl` option to one of the following values, to tell the browser which behavior you prefer for a session:
* `"default"` - Let the browser use its default congestion-control behavior.
* `"throughput"` - Favor the amount of data that's sent over time.
* `"low-latency"` - Favor a low delay in delivering data.

The browser uses your preference to select suitable congestion-control behavior for each session.

See also:
* [WebTransport: congestionControl property](https://developer.mozilla.org/docs/Web/API/WebTransport/congestionControl) at MDN.
* [`congestionControl`, of type WebTransportCongestionControl, defaulting to `"default"`](https://www.w3.org/TR/webtransport/#dom-webtransportoptions-congestioncontrol) in _WebTransport_ at W3C.


<!-- ------------------------------ -->
#### WebTransport: Keying material export

Use the new `WebTransport.exportKeyingMaterial()` method to derive cryptographic keying material that's bound to an established `WebTransport` session.

The `exportKeyingMaterial()` method takes binary `label` and `context` values that you provide, and the length of the output that you want.  It returns a promise that resolves with a `Uint8Array`.  The `label` and `context` values can be up to 255 bytes.  The output length can be from 1 through 4096 bytes.

Different `WebTransport` sessions derive different keying material, even when they share the same underlying HTTP/3 connection.

See also:
* [WebTransport: exportKeyingMaterial() method](https://developer.mozilla.org/docs/Web/API/WebTransport/exportKeyingMaterial) at MDN.
* [`exportKeyingMaterial(BufferSource label, BufferSource context, unsigned long outputLength)`](https://www.w3.org/TR/webtransport/#dom-webtransport-exportkeyingmaterial) in _WebTransport_ at W3C.


<!-- ------------------------------ -->
#### WebTransport: `WebTransportError` alignment and serialization

`WebTransportError` now matches the current WebTransport specification:
* It has the standard `(message, options)` constructor.  The dictionary constructor that was already available still works, for compatibility.
* It carries the full unsigned-long stream error code.
* It's structured-clonable, so you can pass it to other contexts, such as by using `postMessage()`.  The cloned error preserves its `message`, `source`, and nullable `streamErrorCode`.

See also:
* [WebTransportError](https://developer.mozilla.org/docs/Web/API/WebTransportError) at MDN.
* [`WebTransportError` interface](https://www.w3.org/TR/webtransport/#web-transport-error-interface) in _WebTransport_ at W3C.
* [How to use WebTransport](https://developer.chrome.com/docs/capabilities/web-apis/webtransport) at Chrome for Developers.
