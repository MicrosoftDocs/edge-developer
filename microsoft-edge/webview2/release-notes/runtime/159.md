## Breaking change: The WebView2 flag `msAbydosHandwritingAttr` will be removed

_todo: match .doc more closely_

Starting with v159, WebView2 will remove the deprecated `msAbydosHandwritingAttr` browser flag.  After this change, passing `msAbydosHandwritingAttr` through `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, registry-based browser arguments, or `CoreWebView2EnvironmentOptions.AdditionalBrowserArguments` will no longer enable the expected behavior.

This breaking change is planned to ship in WebView2 Runtime 159.  The detailed version number of the WebView2 Runtime, and the release date, are TBD.


<!-- ------------------------------ -->
#### What this means for your app 

Please review your WebView2 app and test configuration, and plan accordingly. 

* If your WebView2 app doesn't set the flag `msAbydosHandwritingAttr`, no action is required.

* If your WebView2 app or your test tooling sets the `msAbydosHandwritingAttr` flag, remove the flag, and validate handwriting scenarios without it.

* Enterprise deployments that configure browser arguments through environment variables or registry settings: remove the flag from managed configuration.

## Breaking change: ACL requirements for Fixed Version deployments 

_todo: match .doc more closely_


<!-- ------------------------------ -->
#### Required ACL setup for app-managed WebView2 Fixed Version runtimes on Windows

Starting with v159, WebView2 is strengthening the renderer sandbox for app-managed Fixed Version deployments.  WebView2 apps that deploy and manage an unpackaged Fixed Version WebView2 Runtime must configure and preserve the required Windows access control list (ACL) entries on the Runtime folder during installation, during Runtime updates, and repair.
<!-- todo: clarify 'repair', orig wording: 
"configure and preserve the required Windows access control list (ACL) entries on the runtime folder during installation, runtime updates, and repair."

This guidance applies to app-managed, unpackaged Fixed Version deployments (of the WebView2 Runtime) on Windows 10 and Windows 11.  Evergreen deployments (of the WebView2 Runtime) and Windows-managed package folders do not require this installer action. 

This breaking change is planned to ship in WebView2 Runtime 159.  The detailed version number of the WebView2 Runtime, and the release date, are TBD.


<!-- ------------------------------ -->
#### What this means for your app 

If your WebView2 app uses the Evergreen WebView2 Runtime, no ACL action is required for Microsoft-managed runtime files. 

Packaged apps and Windows-managed package locations: do not manually modify package-folder ACLs. 

App-managed, unpackaged Fixed Version Runtime: update your installer, updater, and repair flow to configure and verify the required permissions. 


<!-- ------------------------------ -->
#### Required setup 

Run the following commands from an appropriately elevated installer context, replacing {Fixed Version path} with the runtime folder deployed by your application: 

`icacls "{Fixed Version path}" /grant *S-1-15-2-2:(OI)(CI)(RX)`

`icacls "{Fixed Version path}" /grant *S-1-15-2-1:(OI)(CI)(RX)`

These entries grant inheritable read-and-execute access to `ALL RESTRICTED APPLICATION PACKAGES` and `ALL APPLICATION PACKAGES`.  Preserve the runtime folder's existing permissions. 


<!-- ------------------------------ -->
#### How to prepare 

* Add the ACL setup to installation, runtime update, and repair paths. 

* After each deployment operation, verify that both identities have read-and-execute access on the runtime folder and its contents. 

* Run the installed app as a normal user and exercise every WebView2 feature your app depends on; initial page loading alone is not sufficient validation. 

* Handle WebView2 `process-start` or `access-denied` failures with an actionable repair path. 

* Do not use `no-sandbox` or another sandbox-disabling switch as a workaround. 


<!-- ------------------------------ -->
#### Learn more 

* [Fixed Version runtime distribution mode](../../concepts/distribution#the-fixed-version-runtime-distribution-mode.md) in _Distribute your app and the WebView2 Runtime_.

## Breaking change: Stricter File System Access directory checks 

_todo: match .doc more closely_

This breaking change is planned to ship in WebView2 Runtime 159.  The detailed version number of the WebView2 Runtime, and the release date, are TBD.

WebView2 will apply stricter restricted-folder checks during File System Access directory traversal on Windows 


<!-- ------------------------------ -->
#### Stricter restricted-folder checks during File System Access directory traversal 

WebView2 on Windows will align more closely with Chromium security behavior by applying sensitive-location checks when web content accesses or enumerates entries beneath a granted directory. 

This change can affect apps that expose the File System Access API to web content or delegate access to folders under protected system or profile locations. Please review your file-access design and plan accordingly. 


<!-- ------------------------------ -->
#### Release timeline (tentative) 

* October 2026 — advance announcement. 

* Migration window — approximately 2 months after announcement; final dates are pending release-owner confirmation. 

* [Requires release-owner confirmation] — stricter checks reach a WebView2 preview channel. 

* [Requires release-owner confirmation] — enforcement reaches the Evergreen Stable Runtime and the corresponding Fixed Version release. 


<!-- ------------------------------ -->
#### What this means for your app 

* Apps that do not use the File System Access API: no action required. 

* Apps that enumerate user-selected directories: linked or protected child entries might now return an access-denied result. 

* Apps that intentionally access data beneath restricted locations: direct File System Access workflows might stop working and require a storage or host-integration change. 

* Host-delegated workflows: review whether the granted location, its children, or any linked targets fall under restricted-location policy. 


<!-- ------------------------------ -->
#### How to prepare 

1. Move app-managed data required by web content to an appropriate non-restricted location where possible. 

2. If protected data must remain in place, expose only the minimum necessary operations through a validated host-mediated interface rather than broad direct file-system access. 

3. Handle access-denied outcomes gracefully and provide an actionable user recovery path. 


<!-- ------------------------------ -->
#### About restricted folders 

The restricted-location policy is security-sensitive and can evolve. Microsoft will not publish or guarantee an exhaustive directory list. Do not hard-code a folder list or assume a location is allowed because it is not named in documentation. Chromium's public guidance likewise describes restricted folders and examples without publishing an exhaustive blocklist. 


<!-- ------------------------------ -->
#### Learn more 

* [Restricted folders](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access#restricted_folders) in _File System Access API_ in Chrome docs.
