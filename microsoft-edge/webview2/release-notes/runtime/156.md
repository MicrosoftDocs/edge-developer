Release notes for Microsoft Edge WebView2 Preview Runtime, release date: Oct. 12, 2026.

<!-- todo: remove paragraphs when this runtime gets released as a stable runtime -->
This is a Preview Runtime, for early testing.  Prerelease testing of WebView2 SDKs uses a preview channel of Microsoft Edge (Beta, Dev, or Canary), which includes the WebView2 Preview Runtime.

These release notes are for the WebView2 Preview Runtime, which corresponds to the Beta preview channel of Microsoft Edge.  We recommend testing your app using the Beta preview channel of Microsoft Edge, before these changes are promoted to Stable.  If you want to test even earlier, you can test against Edge Dev or Edge Canary.

See [Prerelease testing using preview channels of Microsoft Edge](../../how-to/prerelease-testing.md).

## Breaking change: Removing the `msAbydosHandwritingAttr` WebView2 browser flag
<!-- todo: copy section into 159.md when exists -->

Starting with v159, WebView2 will remove the deprecated `msAbydosHandwritingAttr` browser flag.  After this change, passing `msAbydosHandwritingAttr` through `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, registry-based browser arguments, or `CoreWebView2EnvironmentOptions.AdditionalBrowserArguments` will no longer enable the expected behavior.

Please review your app and test configuration, and plan accordingly.


<!-- ------------------------------ -->
#### What this means for your app

* Apps that don't set `msAbydosHandwritingAttr`:

   No action required.

* Apps or test tooling that set the `msAbydosHandwritingAttr` flag:

   Remove the `msAbydosHandwritingAttr` flag, and validate handwriting scenarios without it.

* Enterprise deployments that configure browser arguments through environment variables or registry settings:

   Remove the `msAbydosHandwritingAttr` flag from managed configuration.

## Breaking change: Required ACL setup for app-managed WebView2 Fixed Version runtimes on Windows
<!-- todo: copy section into 159.md when exists -->

Starting with v159, WebView2 is strengthening the renderer sandbox for app-managed Fixed Version deployments.  Applications that deploy and manage an unpackaged Fixed Version runtime must configure and preserve the required Windows access control list (ACL) entries on the runtime folder during installation, runtime updates, and repair.

This guidance applies to app-managed, unpackaged Fixed Version deployments on Windows 10 and Windows 11.  Evergreen deployments and Windows-managed package folders do not require this installer action.


<!-- ------------------------------ -->
#### What this means for your app

* Evergreen Runtime:

   No ACL action required for Microsoft-managed runtime files.

* Packaged apps and Windows-managed package locations:

   Do not manually modify package-folder ACLs.

* App-managed, unpackaged Fixed Version Runtime:

   Update your installer, updater, and repair flow to configure and verify the required permissions.


<!-- ------------------------------ -->
#### Required setup

Run the following commands from an appropriately elevated installer context, replacing `{Fixed Version path}` with the runtime folder that's deployed by your application:

```
icacls "{Fixed Version path}" /grant *S-1-15-2-2:(OI)(CI)(RX)
```

```
icacls "{Fixed Version path}" /grant *S-1-15-2-1:(OI)(CI)(RX)
```

These entries grant inheritable read-and-execute access to ALL RESTRICTED APPLICATION PACKAGES and ALL APPLICATION PACKAGES.  Preserve the runtime folder's existing permissions.


<!-- ------------------------------ -->
#### How to prepare

1. Add the ACL setup to installation, runtime update, and repair paths.

1. After each deployment operation, verify that both identities have read-and-execute access on the runtime folder and its contents.

1. Run the installed app as a normal user, and exercise every WebView2 feature that your app depends on.  Initial page loading alone is not sufficient validation.

1. Handle WebView2 `process-start` or `access-denied` failures with an actionable repair path.

1. Do not use `no-sandbox` or another sandbox-disabling switch as a workaround.

* [The Fixed Version runtime distribution mode](../../concepts/distribution.md#the-fixed-version-runtime-distribution-mode) in _Distribute your app and the WebView2 Runtime_.

## Breaking change: Stricter File System Access directory checks
<!-- todo: copy section into 159.md when exists -->

Starting with v159, WebView2 will apply stricter restricted-folder checks during File System Access directory traversal on Windows.

WebView2 on Windows will align more closely with Chromium security behavior by applying sensitive-location checks when web content accesses or enumerates entries beneath a granted directory.

This change can affect apps that expose the File System Access API to web content or delegate access to folders under protected system or profile locations.  Please review your file-access design and plan accordingly.


<!-- ------------------------------ -->
#### Release timeline (tentative)

* October 2026 — Advance announcement.

* Migration window — Approximately 2 months after announcement; final dates are pending release-owner confirmation.

* [Requires release-owner confirmation] — Stricter checks reach a WebView2 preview channel.

* [Requires release-owner confirmation] — Enforcement reaches the Evergreen Stable Runtime and the corresponding Fixed Version release.


<!-- ------------------------------ -->
#### What this means for your app

* Apps that don't use the File System Access API:

   No action required.

* Apps that enumerate user-selected directories:

   Linked or protected child entries might now return an `access-denied` result.

* Apps that intentionally access data beneath restricted locations:

   Direct File System Access workflows might stop working and require a storage or host-integration change.

* Host-delegated workflows:

   Review whether the granted location, its children, or any linked targets fall under restricted-location policy.


<!-- ------------------------------ -->
#### How to prepare

1. Move app-managed data required by web content to an appropriate non-restricted location, where possible.

2. If protected data must remain in place, expose only the minimum necessary operations through a validated host-mediated interface, rather than broad, direct file-system access.

3. Handle access-denied outcomes gracefully, and provide an actionable user recovery path.


<!-- ------------------------------ -->
#### About restricted folders

The restricted-location policy is security-sensitive and can evolve.  Microsoft will not publish or guarantee an exhaustive directory list.  Do not hard-code a folder list or assume that a location is allowed because it isn't named in documentation.  Chromium's public guidance likewise describes restricted folders and examples, without publishing an exhaustive block list.


<!-- ------------------------------ -->
#### Learn more

* [Restricted folders](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access#restricted_folders) in _The File System Access API: simplifying access to local files_, in Chrome docs.
